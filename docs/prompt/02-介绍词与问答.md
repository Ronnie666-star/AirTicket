## 一、开场介绍词（约 30~40 秒）

> 老师好，我演示的课程设计是 **AirTicket 飞机票订票系统**。
> 它覆盖了机票交易的完整链路：**登录注册、航班搜索、选舱下单、模拟支付、出票、核销、退订退款、改签**，还带一个管理后台和**3 个统计功能**。
> 技术上后端是 **Spring Boot 3 + MyBatis + Flyway + MySQL**，前端是 **Vue 3**，数据库由 Flyway 版本化管理，内置了 **42 个航班、66 张订单**等共 **175 条实体数据、约 374 条关联关系**，满足演示要求。
> 系统有**三种角色**：管理员、商家、旅客，各司其职。下面我先走一遍旅客从订票到退改签的完整流程，再演示三个统计功能。

## 二、演示流程逐段介绍词

### 1）角色与权限（对应"需求分析"）
🖥 登录页输入 `admin01`（管理员）→ 可以看到「用户管理 / 数据统计 / 基础数据 / 放票管理」；切到 `merch01`（商家）→ 只有「放票管理」；切到 `user001`（旅客）→ 只有「搜航班 / 我的订单 / 个人中心」。

📄 权限实现的 SQL 就是登录查询 + 角色判断：
```sql
SELECT id, username, password, role, status FROM sys_user WHERE username = ?;
```
密码用 **BCrypt 哈希**比对；登录成功后签发 **JWT**，每次请求由过滤器解析出 `userId + role`，再配合 `@RequireRole` 注解拦截角色权限。

💡 加分点：**前端导航也按角色动态显示**，未登录连搜索都进不去（路由守卫）。

### 2）搜索航班（对应"查询功能"）
🖥 在搜索页选「北京 → 上海」+ 日期，点搜索，出现航班列表，显示起降时间、三舱价格（经济/商务/头等）、余票。

📄 对应的搜索 SQL（动态条件）：
```sql
SELECT f.id, f.code, f.datetime_dep, f.datetime_arr,
       f.price, f.price_business_class, f.price_first_class,
       f.seat_economy_class, f.seat_business_class, f.seat_first_class
FROM flight f
WHERE f.datetime_dep >= #{now}            -- 只显示没起飞的
  AND f.status <> 'CANCELLED'             -- 隐藏已取消航班
  AND f.region_dep = '北京'               -- 起降地条件
  AND f.region_arr = '上海'
  AND f.datetime_dep >= '2026-09-01 00:00:00'
  AND f.datetime_dep <  DATE_ADD('2026-09-01 00:00:00', INTERVAL 1 DAY)
ORDER BY f.datetime_dep, f.id
LIMIT 0, 10;
```

💡 加分点：搜索页自动**隐藏已起飞/已取消航班**；`flight` 表有 `(code, datetime_dep)` 唯一索引和地区字段索引，查询走索引。

### 3）航班详情 + 实时轨迹（对应"实时轨迹"）
🖥 点进某个航班，能看到完整信息；再点「实时轨迹」，看到该航班的高度、速度、经纬度、剩余距离/时间。

📄 轨迹查询：
```sql
SELECT distance_remain, time_remain, altitude, speed, latitude, longitude, time_stamp
FROM route WHERE id_flight = 1;   -- route 与 flight 是 1:1
```

💡 加分点：`route` 表和 `flight` 是 **1 对 1** 联系，存的是飞行中的实时状态快照。

### 4）选舱下单（对应"订票功能 / 并发防超卖"）
🖥 选「经济舱」下单 → 订单生成，状态"待出票 / 未支付"，对应舱位余票 -1。

📄 订票是**先加锁读航班、再扣余票、再插订单**，三步在一个事务里：
```sql
-- ① 行锁：把这条航班记录锁住，别人改不了，防止两个旅客同时买最后一张票
SELECT * FROM flight WHERE id = 1 FOR UPDATE;
-- ② 扣经济舱余票
UPDATE flight SET seat_economy_class = seat_economy_class - 1 WHERE id = 1;
-- ③ 插入订单
INSERT INTO orders (id_flight, id_user, id_channel, code, cabin_class, total_price, ...)
VALUES (1, 101, 1001, 'ATxxxxxx', 'ECONOMY_CLASS', 1180.00, ...);
```

💡 加分点（**高频考点**）：**用 `SELECT ... FOR UPDATE` 行锁防超卖**。两张票同时买最后一张时，第二条会等第一条提交再读，绝不会超卖。订单号还有唯一索引兜底，撞号自动重试。

### 5）两段式模拟支付（对应"支付功能"）
🖥 点「去支付」→ 订单变"支付中"，弹出模拟渠道的支付单号 → 点「确认支付成功」→ 订单变"已支付 / 已出票"，记下支付时间、出票时间。

📄 支付分两步：`pay()` 把订单从"未支付"改成"支付中"（生成内存支付单模拟第三方渠道）；`confirm()` 确认后改成"已支付 + 已出票"：
```sql
-- 发起支付（加锁）
SELECT * FROM orders WHERE id = 8 FOR UPDATE;
UPDATE orders SET pay_status = 'PROCESSING' WHERE id = 8;
-- 确认支付成功
UPDATE orders SET pay_status = 'PAID', order_status = 'ISSUED_TICKET',
       pay_time = NOW(), issue_time = NOW() WHERE id = 8;
```

💡 加分点：**模拟了真实第三方渠道的两段式**——支付中状态、用户确认/渠道回调两个入口复用同一套状态机；**支付失败会自动回补余票**，保证座位账平衡；如果支付到一半系统重启，启动时有"自愈"任务把遗留"支付中"订单回退并回补座位。

### 6）退订退款（对应"退订功能"）
🖥 在「我的订单」里对一张已出票订单点「退订」→ 显示退款金额 = 总价 − 退票费，订单变"已退订 / 已退款"，余票回补。

📄 退票费是**动态计算、不落库**的：
```
退款金额 = max(0, 订单总价 − 该航班退票费)
```
```sql
-- 加锁读订单 + 置退订
UPDATE orders SET order_status = 'REFUNDED', pay_status = 'REFUNDED',
       cancel_time = NOW() WHERE id = 8;
-- 回补经济舱余票
UPDATE flight SET seat_economy_class = seat_economy_class + 1 WHERE id = 1;
```

### 7）核销（对应"核销功能"）
🖥 商家 `merch01` 登录 → 放票管理 → 核销一张已出票订单。

📄 核销就是改订单状态（仅商家/管理员有权限）：
```sql
UPDATE orders SET order_status = 'VERIFIED' WHERE id = 8;
```

### 8）改签（对应"改签功能"）
🖥 对已出票订单点「改签」，选同航司的另一趟航班 → 显示价差"多退少补"，订单变"已改签"。

📄 改签约束 + 价差：
```
限制：同航司（通过机型→航司判定）、旧航班未起飞、同舱互换余票
价差 = 新航班该舱票价 − 旧航班该舱票价   → 放入响应(adjustAmount)
```
```sql
UPDATE orders SET id_flight = 3, order_status = 'RESCHEDULED' WHERE id = 8;
UPDATE flight SET seat_economy_class = seat_economy_class - 1 WHERE id = 3;   -- 新航班扣座
UPDATE flight SET seat_economy_class = seat_economy_class + 1 WHERE id = 1;   -- 旧航班回座
```

### 9）管理后台（对应"管理员功能"）
🖥 管理员演示：用户管理（创建商家 `merch03`、禁用/启用、重置密码）、基础数据维护（增删航司/机场/机型/渠道，删除被引用的数据会被保护拦截）。

📄 删除保护用**引用计数**检查：
```sql
SELECT COUNT(*) FROM orders WHERE id_flight = 5;   -- 有订单的航班禁止删除
```

## 三、3 个统计功能介绍词（每个都是"功能 + SQL"）

> 这是「至少 3 个统计功能」的 16 分部分，**每个统计都要边点边说对应的 SQL**。

### 统计① 热门航班销量 Top10
🖥 打开「数据统计」→ 第一块图：横向条形图，展示销量最高的 10 趟航班，旁边标订单数、成交金额、座舱利用率。

📄 SQL（按订单数降序，关联航班和机型算容量）：
```sql
SELECT f.code, f.region_dep, f.region_arr, COUNT(o.id) AS order_count,
       COALESCE(SUM(CASE WHEN o.pay_status IN ('PAID','REFUNDED')
                         THEN o.total_price ELSE 0 END), 0) AS revenue,
       (p.max_seat_first_class + p.max_seat_business_class + p.max_seat_economy_class) AS capacity
FROM flight f
LEFT JOIN plane p ON f.id_plane = p.id
LEFT JOIN orders o ON o.id_flight = f.id AND o.order_status <> 'CANCELLED'
GROUP BY f.id, f.code, f.region_dep, f.region_arr, f.datetime_dep, p.max_seat_first_class, ...
ORDER BY order_count DESC, revenue DESC
LIMIT 10;
```
💡 讲法：**订单数就是已售座位数**（一单一座），`capacity` 是机型三舱上限之和，**利用率 = 订单数 / 容量**，这一条 SQL 同时给出了销量、金额、利用率三个维度。

### 统计② 营收总览 + 渠道营收占比
🖥 第二块：六个 KPI 数字（成交总额、实收营收、退款总额、退票费收入、已支付订单数、订单总数）+ 渠道占比条形图。

📄 SQL（整表聚合 + 渠道分组）：
```sql
-- 总览：一行汇总
SELECT COALESCE(SUM(CASE WHEN o.pay_status IN ('PAID','REFUNDED') THEN o.total_price ELSE 0 END),0) AS total_revenue,
       COALESCE(SUM(CASE WHEN o.pay_status = 'PAID' THEN o.total_price ELSE 0 END),0) AS collected_revenue,
       COALESCE(SUM(CASE WHEN o.pay_status = 'REFUNDED' THEN o.total_price ELSE 0 END),0) AS refund_amount,
       COALESCE(SUM(CASE WHEN o.order_status = 'REFUNDED' THEN f.cancellation_fee ELSE 0 END),0) AS cancellation_fee_income,
       COALESCE(SUM(CASE WHEN o.pay_status = 'PAID' THEN 1 ELSE 0 END),0) AS paid_order_count,
       COUNT(*) AS total_order_count
FROM orders o LEFT JOIN flight f ON o.id_flight = f.id;

-- 渠道占比：按渠道分组
SELECT ch.channel_name, COUNT(o.id) AS order_count,
       COALESCE(SUM(CASE WHEN o.pay_status IN ('PAID','REFUNDED') THEN o.total_price ELSE 0 END),0) AS revenue
FROM channel ch LEFT JOIN orders o ON o.id_channel = ch.id
GROUP BY ch.id, ch.channel_name ORDER BY revenue DESC;
```
💡 讲法：口径统一——**成交金额 = 已支付/已退款订单金额之和**，实收只算已支付，退款单独统计；退票费收入是从 `flight.cancellation_fee` 聚合出来的。渠道占比用 `LEFT JOIN`，连没有订单的渠道也显示。

### 统计③ 旅客消费排行 Top10
🖥 第三块：消费最高的 10 位旅客，标单量和成交金额。

📄 SQL（`sys_user JOIN orders`，只算成交过的订单）：
```sql
SELECT u.username, u.real_name, COUNT(o.id) AS order_count,
       COALESCE(SUM(o.total_price), 0) AS total_spend
FROM sys_user u
JOIN orders o ON o.id_user = u.id
WHERE o.pay_status IN ('PAID', 'REFUNDED')
GROUP BY u.id, u.username, u.real_name
ORDER BY total_spend DESC, order_count DESC
LIMIT 10;
```

## 四、可能问答（老师问 → 你答）

### Q1 系统里有哪些角色？怎么保证权限？
**答**：三种——**管理员（初始化创建）、商家（管理员分配）、旅客（自助注册）**。前端路由按角色拦截，后端每个接口用 `@RequireRole` 注解 + 拦截器校验，双重保险。密码是 BCrypt 哈希，登录签发 JWT，请求带 token 鉴权。

### Q2 有几张表？表和表之间是什么关系？
**答**：**9 张表**。核心关系：
- `airline`(航司) **1:N** `plane`(机型) **1:N** `flight`(航班)，航班再 **N:1** `airport`（出发/到达各一个机场）；
- `flight` **1:N** `orders` **N:1** `sys_user`（一个用户多张订单），订单 **N:1** `channel`（渠道）；
- `flight` **1:1** `route`（轨迹）；
- `sys_user` **1:N** `passenger` **N:1** `sys_user`（常乘机人，自关联）。

### Q3 演示数据有多少？怎么满足"实体≥30、关联≥200"？
**答**：V6 迁移内置 **42 个航班 + 66 个订单 + 12 个用户 + 6 航司 + 10 机场 + 10 机型 + 3 渠道 + 12 轨迹 + 14 常乘机人**，实体共 **175 条**。关联关系数：每张订单 3 条外键（航班/用户/渠道）→ 66×3=198，加航班外键 42×3、轨迹、机型、常乘机人 14×2，合计约 **374 条**，两项都远超课程要求。

### Q4 怎么防止"超卖"？（并发/事务，高频考点）
**答**：下单、支付、退订、改签这些写操作**全部 `@Transactional` 事务 + `SELECT ... FOR UPDATE` 行锁**。比如订票：先锁住航班行，别人只能等，锁内判断余票够不够再扣，所以不会超卖。订单号还有唯一索引兜底，撞号自动重试。

### Q5 建了哪些索引？为什么？
**答**：
- `flight(code, datetime_dep)` **唯一索引** —— 一趟航班唯一，且是精确查询路径；
- `flight(region_dep, region_arr, datetime_dep)` 地区+日期 —— 搜索页最常用；
- `orders(id_flight)` —— 航班取消要按航班找订单，避免全表扫；
- `orders(id_user)` / `orders(code)` —— 按用户查订单、按订单号查；
- `route(id_flight)` 唯一索引、`sys_user(username)` 唯一索引、`airport(region)` 地区索引。

### Q6 统计功能用了什么 SQL？讲一个。
**答**：三个统计都是**聚合查询**。热门航班用 `GROUP BY + COUNT + SUM(CASE WHEN...)` 一次算出订单数/金额/容量；营收总览用 `SUM(CASE WHEN ...)` 一行汇总成交、实收、退款、退票费；旅客排行是 `sys_user JOIN orders` 按人分组排序。核心是 `CASE WHEN` 条件聚合 + `LEFT JOIN` 保证无数据也显示。（详见本文档第三节，可当场打开「数据统计」对应。）

### Q7 订单状态是怎么流转的？
**答**：下单→**待出票/未支付**；发起支付→**支付中**；确认/回调成功→**已支付/已出票**；商家核销→**已核销**；退订→**已退订/已退款**；改签→**已改签**；未支付取消→**已取消**；航班取消→订单**已取消+全额退款**。状态存在 `orders.order_status / pay_status` 两列，领域层用状态机保证非法流转会报错。

### Q8 退票费怎么算？
**答**：**退款 = max(0, 订单总价 − 航班退票费)**，退票费存在 `flight.cancellation_fee`，退款金额**动态计算放进响应、不落库**，避免和订单状态产生冗余矛盾。

### Q9 为什么支付要"两段式"？"支付中"的订单崩溃了怎么办？
**答**：为了模拟真实第三方支付渠道——先发起生成支付单（订单进"支付中"），再等用户确认或渠道回调，成功后置"已支付/已出票"。**支付失败自动回补余票**；启动时有个**自愈任务**，把残留的"支付中"订单全部回退成"未支付"并回补座位，保证重启不丢账。

### Q10 改签为什么限制同航司？多退少补怎么算？
**答**：改签本质是"换一趟航班"而不是"退票再买"，所以限定**同航司**（通过机型→航司关联判断）、**旧航班未起飞**、**同舱级互换余票**。价差 = **新航班该舱票价 − 旧航班该舱票价**，放响应里多退少补。

### Q11 怎么做到"只能查自己的订单"？
**答**：查询订单的 SQL 里**恒有 `AND o.id_user = #{userId}`**，而 `userId` 是从 JWT 里取的，**不由前端传**，所以伪造不了别人的查询。查详情时归属不符统一返回 404，不泄露信息。

### Q12 三舱（头等/商务/经济）怎么设计的？
**答**：`flight` 表存三舱**余票** `seat_first/business/economy_class` 和三种**票价** `price`（经济）、`price_business_class`、`price_first_class`；`orders` 表加一列 `cabin_class` 存舱级。下单按舱扣座、按舱计价，退订按舱回补，改签按同舱算价差——三处逻辑用统一的 `seatOf/priceOf` 方法，不会改漏。

### Q13 数据量大了怎么优化？
**答**：**常用查询列建索引**（B+ 树二分查找）、表按时间**分区**、冷热数据分表、必要时**读写分离/分库分表**（MyCat/ShardingSphere）。本项目演示规模用索引就够，方案在报告里写了。

### Q14 数据库表结构怎么管理的？
**答**：用 **Flyway 版本化迁移**：`V1` 建 9 张表，`V3` 加舱级和三舱价，`V4` 加航班归属，`V5` 加订单航班索引，`V6` 灌演示数据。每次启动自动检测并执行新版本，团队/换机器环境一致，不会"建表脚本对不上"。

### Q15 前端有什么亮点？
**答**：Vue3 组件化，统一了 **Apple 风格设计系统**：设计令牌（`tokens.css` 里的颜色/字号/圆角/间距变量）+ 复用组件（卡片/按钮/弹窗/骨架屏），所有页面只用令牌取值，观感一致。角色导航、路由守卫、错误提示友好化，操作简单。

### Q16 演示时如果老师问你"支付成功了但显示失败"怎么办？
**答**：我们的座位账是平衡的——**支付失败会回补余票，重新支付会再扣回**，支付单是内存存储、启动自愈兜底，所以不会出现"钱收了票没了"或"票卖了没扣座"。这一点在健壮性设计里专门讲过。
